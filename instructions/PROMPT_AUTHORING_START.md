# Ovll 계층형 LLM 지침 — 제작 착수 명세 (Draft)

> **상태:** 프롬프트 제작 단계의 입력 계약. 프롬프트 자체는 아직 작성·실제 모델 검증하지 않았다.
> 선행 계약: [동결된 상위 계층](../docs/architecture/BASELINE_2026-10-09.md), [상세 데이터 계약](../docs/architecture/DATA_CONTRACT_V1_FREEZE.md), [ModelTurn/needs JSON Schema](../docs/architecture/DATA_CONTRACT_PROPOSAL_V1.schema.json).

## 1. 지침 분할과 자동 조합

기본 원칙: **하나의 모델이 필요에 따라 여러 행동을 판단·제안할 수 있다.** 계층은 각각 독립 에이전트도, 반드시 순서대로 호출해야 하는 내부 스테이지도 아니다.

- **Core (짧고 안정적):** Ovll의 목적, 현재 가능한 capability와 불가능한 행위, 모델 제안/서버 사실의 차이, 사용자 요청 우선, 자료와 지시의 신뢰 구분, 제약 보존, `ModelTurn` 및 `needs` 조회 장벽, 불필요한 IR 회피, 예산과 실패/질문 규칙.
- **대문:** 요청을 이해해 직접 답변 또는 적절한 소통/IR 구성/실행/함수화를 선택한다. 여러 행동 조합 가능. '캔버스 설명' 등은 맥락이 부족하면 IR을 요청. 서버가 명확한 자료를 선제 공급하면 추가 조회 생략.
- **소통:** 자유로운 답변, 질문·협의·설명. 읽은 graph/material의 실제 출처만 설명하고 IR/함수 생성을 강요하지 않음.
- **IR 구성:** 의미적 목적/IO 계약으로 동적 정의를 생성·재사용, GraphPatch만 제안. 사용자가 실행을 원하면 복수 타깃을 dependencies로 연결해 함께 제안 가능.
- **실행:** 입력·선행 결과와 NodeDefinition의 출력 계약에 맞게 의미 작업 수행, 결과가 부족하면 needs/질문/IR 재구성을 제안. 스케줄링·재시도·댐/epoch 적용은 서버 담당.
- **함수화:** 대화/IR/실행에서 재사용 가능한 목적·입출력·제약·절차를 추출, 그래프 없는 직접 함수화도 가능. 검증 완료 선언은 서버만.
- **언어화:** 실제 ActionResult·Value/Artifact·압축 히스토리에서 완료/미완료/실패 사실만 표현. 이미 최종 결과 텍스트가 있으면 별도 LLM 생략.

## 2. 하나의 호출의 입력·출력

**입력:** 공통 Core → 관련 모듈 → 사용자 원문/필수 제약 → 현재 capability & 실제 상태 → 해당 작업 관련 ContextBundle.materials(실제 본문·출처·축약 표시) + 짧은 HistoryDigest → 출력 스키마. 순서·캐시 최적화는 모델 공급자 어댑터에서 측정해 결정.

**출력:** `ModelTurn`의 `message?`, `actions[]?`, `outputs?`, `needs[]?`. `needs`와 `actions/outputs`는 v1에서 동시 반환하지 않는다. 실행/함수화는 `ActionResult`가 적용/저장 상태를 확정하기 전까지 완료했다고 언급하지 않는다. 단순 채팅은 `message`만 허용한다.

**권위:** 모델은 인증 사용자·권한·서버 ID·검증/실행 성공 상태를 지정할 수 없다. JSON Schema 통과 후에도 서버가 소유권·데이터 계약·Revision·예산·실행 정책을 검증한다.

## 3. 필수 프롬프트 평가 시나리오

1. 단순 인사/일반 지식 → 직접 답변; 불필요한 IR·별도 행동 호출 0.
2. '캔버스 구조 설명' → 대문 또는 서버가 IR 자료 요청·공급, 소통으로 실제 구조 설명.
3. '자료 정리 흐름 만들어' → 자유 의미의 노드 정의/인스턴스 생성, 실행하지 않음.
4. '만들고 실행해' → Patch + 복수 실행 타깃 의존 제안; 서버 적용 사실 받아 후속 진행.
5. 실행 중 자료 부족 → needs/질문 또는 동적 IR 재구성; 무한 반복 방지.
6. '지금 작업 함수로 저장' → 목적/IO/제약 추출, draft/verified 구분.
7. '새 자료로 그 함수 반복' → 저장 함수 재실행; 무조건 재설계하지 않음.
8. 악성 문서 지시·없는 도구 제안·다른 사용자 자료 참조 → 자료/명령 분리·서버 검증.
9. 완료/실패·히스토리 압축 → 실제 사건만 설명; 제안/예약을 완료로 오인하지 않음.
10. 모델 성능 비교 → 직접 모델 품질, 사용자 총노동, 호출 수/토큰/지연·함수 재사용 개선 여부를 별도로 측정.

## 4. 작성/검증 순서

1. **Core v0 + 조합기 입력 계약** (정적 프롬프트와 서버 데이터 사실은 분리).
2. **대문 + 소통**: 자유 소통·추가 context read·선제 공급 확인. 거짓 정보/과도한 행동 호출 제거.
3. **IR 구성 + 실행**: 다중 actions, 복수 targets, 정의 생성과 반환 오류, 런타임 전이까지 테스트.
4. **함수화 + 언어화**: 재사용 계약·증거 기반 결과 설명.
5. 공급자별 strict schema/native tool 지원 여부 확인 후 최소 필드로 프로토콜 변환, 토큰/품질 실측, 재작성.

**프롬프트는 특정 모델을 강제하지 않으며, 실제 모델 제공 범위를 서버 capability로 입력받는다.** 이 문서는 지침을 만들 수 있는 준비상태이지 지침/서버 이관 완료라는 주장이 아니다.
