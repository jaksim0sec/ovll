# Ovll — 작업실 구조 개편 논의 기록

> 2026-10-15 · 설계 논의 기록 · 구현 완료를 의미하지 않음
>
> 이 문서는 대화에서 제안·합의한 내용만 기록한다. 미정인 내부 계약은 확정하지 않는다.

## 1. 개편 취지

기존 `main`에서는 복도가 `actionKinds`로 구체적인 행동 종류까지 정하고, 서버가 해당 행동의 지침과 출력 계약을 조립한 다음 작업실이 행동 인수를 작성한다.

개편 방향은 **복도가 작업실의 목표와 순서를 계획하고, 작업실이 전달된 목표·맥락체를 바탕으로 구체적인 행동을 결정**하도록 바꾸는 것이다.

- 작업실은 너무 포괄적인 기술 계층 하나에 행동을 몰아넣지 않고, **합리적인 행동 책임 단위**로 나눈다. 기존 IR 관련 책임을 스킬 생성·수정과 캔버스 편집 등의 작업실로 나누는 것이 핵심 사례다.
- 복도는 작업실 단위의 `objective`를 전달한다. 작업실은 그 목표 범위 안에서 어떤 행동을 어떻게 수행할지 판단한다.
- 작업실과 행동은 논리적으로 분리한다. 실제 모델 호출은 작업실 기준으로 여러 행동을 묶을 수도 있고, 규모나 필요한 결과 확인에 따라 행동 기준으로 나눌 수도 있어야 한다.
- 작업실 내부는 **Function Calling 방식**으로 전환하는 방향이다. 기존 행동의 의미와 서버 내부 실행 로직을 무작정 합치지 않는다.
- 전체 시스템이 조립식 지침 블록을 사용하는 것처럼, 작업실 내부에서도 **해당 행동을 수행할 때 필요한 전용 프롬프트만 조립**한다.
- 기존 IR·실행기·스케줄러 등은 보존하는 전제다. 이 문서가 새 실행기 설계를 확정하지는 않는다.

## 2. 작업실 및 행동 구성

아래 명칭은 대화에서 최종적으로 정리한 명칭을 사용한다. 스킬은 정의된 작업 그 자체이고, 스킬 블록/스킬 노드는 해당 스킬을 참조하며 캔버스에 배치된 동일 오브젝트의 두 명칭이다. 저장 함수는 별도 자산이다. `skillDefine`의 '정의'는 스킬을 만들거나 수정하는 행위를 뜻하며 별도 자산 종류를 뜻하지 않는다.

| 작업실 / 계획 항목 | 행동 | 합의된 역할 |
|---|---|---|
| `skillDefine` | `defineDirect` | 새 스킬 정의를 직접 작성. 처음 제안된 이름은 `defineByJSON` |
| `skillDefine` | `defineFromIR` | 기존 IR 작업 흐름을 재사용 가능한 함수로 추출·저장. 처음 제안된 이름은 `defineByIR`; 기존 `function.save`의 목적에 대응 |
| `skillDefine` | `revise` | 기존 스킬 정의 수정 |
| `skillEdit` | `editAppearance` | 스킬 외형 편집 |
| `skillEdit` | `delete` | 스킬 삭제 |
| `canvasEdit` | `addBlock` | 캔버스에 스킬 블록(스킬 노드) 추가 |
| `canvasEdit` | `editBlock` | 캔버스의 스킬 블록(스킬 노드) 편집 |
| `canvasEdit` | `deleteBlock` | 캔버스의 스킬 블록(스킬 노드) 삭제. 사용자 초안의 표기는 `delteBlock` |
| `canvasEdit` | `addLink` | 연결 추가 |
| `canvasEdit` | `removeLink` | 연결 제거 |
| `textGenerate` | `basicText` | 사용자에게 자연어 전달 |
| `textGenerate` | `question` | 사용자에게 질문 |
| `terminate` | 없음 | 완전종결을 명시하는 계획 항목 |

- 기존 `question.ask`처럼 질문에만 한정된 인터페이스를 언어 발화에 쓰도록 확대하자는 논의에서 `text.add`가 임시 명칭으로 나왔다. 이후 작업실 명칭은 `language` 대신 **`textGenerate`**로 정리했고 행동은 `basicText`, `question`으로 구분했다.
- `skillDefine` 안에 직접 스킬 정의와 기존 IR에서의 함수 추출을 **논리적으로 함께 배치**하지만, 스킬과 저장 함수는 서로 다른 자산이며 내부 저장·버전·실행 계약을 나눠 처리할 책임은 **서버**에 있다. 둘의 내부 로직을 하나로 합치자는 뜻이 아니다.
- `skillDefine`에서 함수화를 수행할 때 전용 지침을 조건부로 제공하며, **별도 함수화 작업실을 추가하지 않는다**.
- `terminate`는 행동을 담은 일반 작업실이 아니라 완전종결을 나타내는 항목이다.

## 3. 복도 계획과 작업실 자율성

복도에서 각 작업실에 구체적인 행동 명세까지 미리 정해주기보다는 `objective`와 필요한 추가 데이터 조회 `need` 등을 지정한다. 예시로 논의한 계획은 다음과 같다.

```js
[
  {
    skillDefine: {
      objective: "일본어 단어장 스킬 정의",
      need: [["skillList"]]
    }
  },
  {
    canvasEdit: {
      objective: "캔버스에 일본어 단어장 스킬 블록 추가",
      need: []
    }
  },
  {
    terminate: {
      objective: "결과 안내",
      need: []
    }
  }
]
```

위는 **논의한 표현을 읽기 좋게 옮긴 예시**이며, 최종 서버 JSON 스키마 확정안은 아니다. 초기 예시에는 `skillDef`, `irEdit`, `end`라는 이름이 쓰였으나 이후 작업실 명칭을 재정리했다.

- `need`는 별도로 논의한 정보 요청 블록의 데이터셋 조회를 가리킨다.
- `skillList` 조회는 기존에 정의된 스킬이 있는지 판단하기 위한 사례다.
- 캔버스 상태처럼 **서버가 자동으로 제공하는 정보**는 작업실이 불필요하게 `need`로 다시 요청하지 않는다는 원칙을 유지한다.
- 작업실은 자기 목표 안에서 기존 자산의 활용, 신규 정의 생성 등 구체적 접근을 판단한다.
- `skillList`를 조회해 이미 일본어 단어장 스킬이 존재함을 발견했다면, 필요 시 복도에 돌아가 계획을 재검토할 수 있다. 이 경우 확인한 사실을 현재 호출의 관련 맥락으로 전달한다.
- 기존 정의를 발견할 때마다 **반드시 복도회귀해야 한다고 확정한 것은 아니다**. 해당 발견이 현재 계획에 어떤 영향을 주는지가 중요하다.
- 복도회귀 시 서버가 갖고 있는 맥락체·실제 결과를 활용한다. 맥락체는 결과 원본 저장소가 아니다.

## 4. 사용자 발화 및 종결 흐름

스킬 생성 예시에서 바라는 사용자 경험은 다음과 같았다.

1. 작업 도중 간단한 진행 발화를 보여준다. 예: “수준과 일본어를 입력하는 일본어 단어장 스킬을 만들어드릴게요.”
2. 스킬 정의 목표에 따라 해당 작업실이 구체적인 정의 생성 방식을 선택한다.
3. 정의의 저장 및 실제 적용 확인은 서버가 담당한다.
4. 캔버스 추가 목표에 따라 스킬 블록(스킬 노드)을 배치한다.
5. 실제 완료된 결과를 근거로 최종 자연어 응답을 제공한다.

중간 발화는 **언어 생성과 맥락체 갱신 지침의 조립**으로 구성할 수 있다는 논의를 했다.

또한 실행(`execute`)이 있을 때에는 서버가 **언어 생성 + 맥락체 갱신 + 맥락데이터 갱신** 계층으로 보내 종결한다는 방향을 명시했다. 이 논의에서 `execute`를 새로운 독립 작업실로 추가하지 않았다.

### 끝 처리

- 계획에서 `terminate`를 명시하면 **완전종결**한다.
- 계획에 뒤따르는 항목이 없고 `terminate`도 없다면 **복도회귀**한다.
- 작업실에서 계획 전제가 달라지는 관련 사실을 발견한 경우, 복도회귀로 재판단하도록 하는 예시가 논의되었다.

이 규칙 이외의 구체적인 상태 전이·오류 복구·서버 출력 계약은 이 문서에서 임의로 확정하지 않는다.

## 5. 기존 합의와의 연결

- 한 요청 안의 계층 연결에는 **맥락체**를 사용한다. `intent`·`progress`는 맥락체 생성·갱신 블록의 책임이고, `focus`는 서버가 모델 호출마다 구성한다.
- 세션 전체를 위한 **맥락데이터**는 맥락체와 별개로 관리한다.
- 세부 기술 행동과 실행 결과의 처리는 기존 서버 자산의 책임을 보존한다.
- 작업실마다 전체 프롬프트를 고정 탑재하기보다는 필요한 행동별 지침을 선택적으로 조립한다.

## 6. 아직 확정하지 않은 사항

아래는 후속 설계 대상으로 남겨 둔다. 이 문서의 기록만으로 특정 구현을 강제하지 않는다.

- 각 작업실의 정확한 Function Calling 함수 선언·인수 스키마 및 반환 계약
- **작업실 단위로 행동을 묶을지, 행동 단위로 모델 호출을 나눌지** 선택하는 구체적인 조건
- `skillDefine`의 직접 정의와 IR 함수 추출이 공유하는 상위 API 형식 및 각 저장 자산의 내부 매핑
- `execute`의 정확한 계획 표현과 종결 처리 연결 방식
- 작업실의 복도회귀 시 반환 데이터 계약과 계획 재작성 세부 규칙
- 블록 조립 조건, 전체 JSON 머릿글과 서버 호출 상태 전이의 구현 세부

이 문서는 **논의된 작업실 분할과 책임 경계의 기록**이지 `main`이 이미 구현했다는 선언이 아니다.
