# Ovll — 계층 베이스 지침 + 조립식 지침 블록 아키텍처

> 2026-10-15 · 설계 기록 · 합의된 방향을 정리한 문서이며 구현 완료를 의미하지 않음

## 1. 기본 구조

Ovll의 모델 호출 지침은 다음 두 부분을 **서버가 호출 목적에 맞게 조립**한다.

1. **각 계층의 고정된 얕은 베이스 지침** — 해당 계층의 역할과 책임 경계를 짧게 규정한다.
2. **공통 지침 블록** — 호출에서 실제로 필요한 작성 기능만 선택적으로 추가한다.

```text
[해당 계층의 고정된 얕은 베이스 지침]
                +
[필요한 공통 지침 블록 0개 이상]
                +
[서버가 제공하는 맥락·작업 입력·출력 계약]
                ↓
             모델 호출
```

기존처럼 `대문 → 복도 → 작업실 → 출구`의 역할마다 반드시 별도 LLM 호출을 수행하는 것이 아니다. **논리적 계층과 실제 API 호출 경계는 서로 다르다.** 각 계층의 정체성은 얕은 베이스 지침으로 유지하면서, 계획·정보 요청·맥락 갱신·언어화 등은 호출의 필요에 따라 조립한다.

- 목표: 불필요한 호출 감소, 요청 내부 맥락 연결, 필요한 시점의 중간 발화, 저가 Gemini 모델의 부담 감소.
- 보존 대상: 기존 IR, 실행기, 스케줄러(닫힌 댐/열린 댐), 동적 노드 생성·정의, 함수화와 버전 자산.
- 지침 블록 하나가 별도 모델 호출 하나를 뜻하지 않는다.
- 지침 블록은 담당하는 출력의 작성 규칙을 정의한다. 반환 JSON의 공통 머릿글, 최종 출력 스키마 조립 및 실행은 서버 책임이다.

## 2. 지침의 두 종류

### 2.1 계층별 고정 베이스 지침

대문·복도·작업실·언어/출력 등 **각 계층에 해당하는 짧고 고정된 기본 역할 지침**을 둔다. 공통 블록의 설명을 베이스 지침마다 반복하지 않는다.

- **대문**: 사용자 요청의 진입과 초기 맥락·필요 정보 준비.
- **복도**: 현재 요청과 진행 상황을 판단하고 다음 작업실들의 목표·순서를 계획.
- **작업실**: 할당된 목표를 받아 해당 책임 범위의 구체적인 행동을 선택·수행.
- **언어/출력**: 확인된 정보와 결과를 사용자에게 전달하는 역할.

위는 **계층의 책임 요약**이다. 각 계층의 실제 베이스 프롬프트 문구 및 출력 계약이 모두 확정됐다는 뜻은 아니다. 특히 종전의 '복도 판단 블록'은 이번 구조에서는 **복도의 베이스 책임**으로 구분하며 독립 공통 지침 블록 목록에 중복해서 두지 않는다.

### 2.2 선택적으로 조립하는 공통 지침 블록 5종

| 공통 지침 블록 | 모델이 담당하는 내용 | 지침 파일 |
|---|---|---|
| **계획 생성** | 현재 요청을 충족할 순서 있는 작업실 계획 `plan` 작성 | `계획_생성_지침.md` |
| **데이터 요청** | 추가 조회를 위한 `need` 배열 작성 | `데이터_요청_지침.md` |
| **맥락체 갱신** | 단일 요청 내 `contextBlock.intent`, `contextBlock.progress` 생성·갱신 | `맥락체_갱신_지침.md` |
| **맥락데이터 갱신** | 세션 전체의 `contextData` 생성·갱신 | `맥락데이터_생성_지침.md` |
| **언어 생성** | `languageBlock`으로 중간·최종 사용자 발화 작성 | `언어_생성_지침.md` |

'맥락데이터 갱신'은 이 문서에서 역할을 통일해 부르는 명칭이고, 현재 별도 파일명은 `맥락데이터_생성_지침.md`이다. 이 문서 수정만으로 다른 파일을 개명하지 않는다.

- 각각의 블록은 **해당 기능이 필요한 호출에만** 포함한다.
- **데이터 요청 문법은 데이터 요청 지침에만** 정의한다. 계획 생성에서 쓰는 `need`도 동일 규격의 배열을 따른다. 타 블록에서 목록과 문법을 복제하지 않는다.
- 별도의 **맥락체 활용 블록**은 두지 않는다. 맥락체는 서버가 관련 호출의 입력으로 제공하고, 계층과 블록은 자신의 역할에 맞게 참고한다.
- 지침이 호출에 포함되지 않은 기능에 대해 모델이 임의의 필드를 갱신하도록 하지 않는다.

## 3. 계획과 작업실 제어

복도는 개별 행동을 미리 고르는 대신 **작업실 단위**로 `plan`을 작성한다. 계획의 각 단계는 작업실명과 `objective`, `need`를 담는다.

- `objective`: 작업실이 달성할 목표. **실제 UI에 표시되므로 사용자의 언어**를 따르고 자연스럽고 간결하게 기술한다.
- `need`: 데이터 요청 지침 규격 그대로의 배열. 서버가 이미 자동 제공하는 자료를 중복 예약하지 않는다.
- 내부 행동의 구체적 선택은 해당 작업실의 책임이다.

현재 논의한 계획 항목은 `skillDefine`, `skillEdit`, `canvasEdit`, `textGenerate`, `terminate`이다. `terminate`는 일반 작업실의 내부 행동이 아닌 **명시적 완전종결 항목**이다. 세부 행동의 범위는 `작업실_구조_개편.md`에 기록되어 있다.

```json
{
  "plan": [
    {
      "skillDefine": {
        "objective": "일본어 단어장 스킬 정의",
        "need": [["skillList"]]
      }
    },
    {
      "canvasEdit": {
        "objective": "캔버스에 일본어 단어장 추가",
        "need": []
      }
    },
    {
      "terminate": {
        "objective": "작업 결과 안내",
        "need": []
      }
    }
  ]
}
```

위는 계획 형식의 사례이며 실제 작업의 성공 여부를 나타내지 않는다.

- 계획에 `terminate`를 두면 종결한다. 종결 시 서버가 **최종 언어 생성**을 처리하므로 마지막 답변만을 위한 별도 `textGenerate` 단계를 요구하지 않는다.
- 계획이 `terminate` 없이 끝나면 서버는 **복도로 회귀**하여 현재 진행 상태를 다시 판단하고 다음 계획을 생성한다.
- 연속 작업실은 순서대로 수행하며, 반드시 각 작업실 뒤에 복도 판단 호출을 추가하지 않는다.
- 작업실이 계획의 전제를 바꾸는 사실을 발견하면 필요에 따라 복도에서 재판단할 수 있다.
- 실패를 실제 성공으로 간주해서는 안 되며, 실패가 반복되는 경우 무의미한 재계획 루프를 방지해야 한다. 이 부분의 구체적인 복도 베이스 문구와 서버 제어 규칙은 아직 미확정이다.

## 4. 계층별 호출과 조립

아래는 **역할에 따른 조립 방향**이며, 모든 상황의 확정된 호출 매트릭스가 아니다.

| 상황 | 얕은 베이스 역할 | 조립되는 공통 기능 |
|---|---|---|
| 최초 요청 진입 | 대문 | 초기 맥락·정보 준비 (세부 조립 조건 미확정) |
| 최초 복도/복도회귀 | 복도 | **계획 생성**, 필요시 데이터 요청·언어 생성·맥락체 갱신 |
| 개별 작업실 처리 | 해당 작업실 | 담당 행동 지침과 필요한 공통 블록을 조합; 일반 호출에서 맥락체를 무조건 갱신하지 않음 |
| 중간 사용자 발화 | 해당 호출의 베이스 역할 | 필요시 **언어 생성 + 맥락체 갱신** |
| 완전종결 | 언어/출력 역할 | **언어 생성 + 맥락체 갱신 + 맥락데이터 갱신** |

실행(`execute`)과 종결의 연결에 관해서도 **언어 생성 + 맥락체 갱신 + 맥락데이터 갱신을 조립하여 종결**한다는 방향을 논의했다. 이를 이유로 `execute`라는 별도 작업실을 임의로 신설하지 않는다.

작업실은 각기 담당하는 행동을 내부적으로 결정하는 구조를 지향한다. **Function Calling 도입 방향은 합의했으나 정확한 함수 선언·반환 스키마·한 호출에 행동을 묶는 조건은 미확정**이다. 기존 저장/실행 내부 로직을 통째로 합친다는 뜻도 아니다.

## 5. 맥락데이터와 맥락체

| 구분 | 범위 | 필드 및 관리 |
|---|---|---|
| **맥락데이터** `contextData` | 세션 전체 | 모델 작성: `overallFlow`, `currentTopic`, `details` |
| **맥락체** `contextBlock` | 하나의 사용자 요청 처리 내부 | 모델 작성: `intent`, `progress`; 서버 작성: `focus` |

- 맥락데이터는 대화의 전반적인 흐름, 현재 주제, 관련 결정·제약·지속 지시를 보존한다. 단일 요청의 맥락체와 구별한다.
- 맥락체의 `intent`, `progress`는 **맥락체 갱신 지침이 조립된 호출에서만** 생성·변경된다. 일반 작업실 호출에서 자동으로 덮어쓰지 않는다.
- `focus`는 서버가 **모든 모델 호출 때 교체**하여 직전 작업에서 확인된 관련 사실과 현재 호출의 위치·역할을 전달한다.
- **맥락체 작성기는 `focus`의 존재를 알 필요가 없으며**, `intent`, `progress`만 작성한다.
- 실행 원본, 계획 원문, 상세 로그와 산출물은 별도 보관한다. 맥락체에 이를 복제하거나 확인되지 않은 성공을 기록하지 않는다.

맥락체의 자료 구조와 예시는 `맥락체.md`를, 최신 모델 작성 규칙은 `맥락체_갱신_지침.md`를 따른다. 이 문서 안에 오래된 지침 문구를 복제해 별도 버전처럼 유지하지 않는다.

## 6. 설계 확정 범위와 남은 사항

**방향이 정리된 부분**

- 각 계층의 **고정된 얕은 베이스 지침 + 5종 공통 지침 블록**의 선택적 조립.
- 논리적 계층과 개별 모델 호출 경계의 분리.
- 작업실 단위 계획, 작업실 내부 행동 선택.
- `terminate` 종결과, 미기재 시 복도회귀.
- 맥락데이터/맥락체 분리 및 `focus`의 서버 관리.
- 기존 IR·실행·스케줄러·동적 노드 및 함수화 자산 보존.

**구체적 구현 계약이 남은 부분**

- 계층별 베이스 지침 원문과 각 호출에서의 정확한 블록 조립 조건.
- 공통 출력 머릿글, 스키마 조립 및 필드 반환 계약.
- 작업실 Function Calling의 함수 선언·반환 계약 및 호출 묶음 기준.
- 복도회귀·오류 반복 방지의 구체적인 서버 제어 규칙.
- `execute` 처리의 세부 연결.

이 파일은 아키텍처의 **단일 개요 문서**다. 각 지침의 원문은 대응하는 `*_지침.md` 파일에 두고, 상세 작업실 정의는 `작업실_구조_개편.md`에서 관리한다.
