# 요청·호출 수명, 방 데이터, 실시간 동기화 — 논의 노트

출처: `develop-documents/1014/개발문서_임시노트.md`(2026-10-16). **미완성 설계; 구현 계약으로 자동 확정 금지.** 합의 방향·권장안·미정 항목 구분을 유지한다.

## 0. 이 문서의 위치 및 확정 수준

- **[합의된 방향]** 1014의 논리적 계층(Gate, Corridor, Workroom, Output), 맥락체, 맥락데이터, 조립식 지침을 새로운 아키텍처의 기준으로 사용한다.
- **[합의된 방향]** 구형 main의 백엔드/프론트 데이터 구조는 동일하게 재현할 대상이 아니다. 실행 검증, 참조 무결성, IR, 스케줄링, 오류 복구 등의 경험을 추출하는 **참조 구현체/경험 창고**로 본다. 불필요한 용어 변환 계층을 새 설계에 다시 만들지 않는다.
- **[합의된 방향]** 스킬은 정의된 행동 자체다. **스킬블록**은 캔버스에 배치된 스킬 인스턴스다. 둘은 다른 객체이며, 저장 함수도 별도 자산이다. 기존 코드의 node/skill 같은 변수명으로 개념을 자동 대응시키지 않는다.
- **[합의된 방향]** 요청 실행을 관리하는 **공통 기반을 최소한 먼저 만들고**, 작업실을 실제로 연결하면서 점진적으로 검증한다. 공통 기반 전체를 과도하게 완성한 뒤 작업실을 시작하거나, 작업실에 세션/통신 책임을 먼저 집어넣는 방식은 피한다.
- **[미확정]** 최종 모듈명, 저장소명, 세부 JSON 필드, DB 테이블 구조 및 트랜잭션 경계, API URL, SSE 이벤트명, 정확한 직렬화 방식. 이 노트의 예시는 구현 방향을 설명할 뿐 네이밍 확정이 아니다.

## 1. 먼저 분리해야 하는 세 가지 수명

1. **방/세션(room)**: 지속되는 대화방. 한 방에서 복수의 요청이 발생하며, 채팅 기록과 세션 맥락데이터가 축적된다.
2. **개별 요청(request)**: 한 번의 사용자/외부 근원지 요청을 처리하는 독립 실행 단위. 현재 계층, 계획 진행, 맥락체, 중단 상태 등을 가진다. 같은 방에서도 요청 두 개가 동시에 실행될 수 있다는 전제로 설계한다.
3. **프론트 연결(SSE/HTTP)**: 요청을 보내고 진행 상황을 받는 통신 수단. 브라우저가 닫히거나 통신이 끊어졌다고 요청의 실행 수명이 곧바로 종료되는 것은 아니다.

방 ID와 요청 ID는 구분한다. roomId만으로 요청을 구별하면 같은 방의 두 요청 상태와 중단 대상이 충돌한다.

### 1.1 임시 요청 레지스트리(사용자 제안)

개념상 요청을 아래처럼 관리한다.

    requests[roomId][requestId] = {
      currentLayer: "...",
      contextBlock: { intent: "...", progress: "..." },
      userRequest: "...",
      ... // 현재 계획, 실행 상태, 확정 결과 등 추후 논의
    }

- 위 표기는 **접근 구조를 이해하기 위한 예시**이다. 정확한 필드·명칭 및 내부 객체 구조는 확정하지 않았다.
- 요청마다 고유 UUID를 부여하는 방식으로 시작한다. **UUID는 임시 파일/SQL 도입 전용 식별자라는 뜻이 아니다.** SQL 도입 후 요청 ID의 생성 방식은 바꿀 수 있지만, 세션 ID와 **개별 요청 ID라는 두 차원은 계속 필요**하다.
- roomId.requestId는 설명용 복합 표기일 수 있다. DB에 저장할 때는 둘을 개별 필드로 관리할 수 있어야 한다.
- 근원지가 꼭 사용자 채팅일 필요는 없다. 외부 API, 자동화 등 서로 다른 근원지의 요청도 개별적으로 식별/관리해야 한다.
- 임의 UUID 자체를 인증 수단으로 사용하지 않는다. 요청의 소유자/허용된 호출 주체 확인은 별개 문제다.
- 같은 프로세스의 JavaScript 객체를 활용할 수는 있지만, 서버 재시작·다중 인스턴스 환경에서 그 객체 하나만을 영구적인 진실의 원본으로 가정하지 않는다.

### 1.2 요청 단위로 독립되어야 하는 상태

- 사용자/근원지의 요청 원문 및 참조
- 현 실행 상태(running, 중단 요청, 완료, 실패 등)
- 서버가 확정하는 현재 계층 및 필요시 현재 작업실/계획 위치
- 1014 맥락체의 요청 범위 데이터(intent, progress)
- 현재 계획/계획 진행 정보에 대한 참조
- 실제 실행의 검증된 결과 및 그 참조, 오류/대기 상태
- 취소 제어 및 프론트 동기화를 위한 최신 상태 버전/이벤트 순서(구체 형식 미정)

**현재 계층은 서버가 결정**한다. 모델이 응답에 자신의 위치를 주장한다고 해서 그 주장만으로 실행 위치를 수정하지 않는다.

## 2. 1014 맥락체와 맥락데이터의 정확한 위치

기존 문서 docs/developing/context.md 및 docs/developing/architecture.md의 원칙을 그대로 따른다.

| 데이터 | 생명주기/소속 | 관리 원칙 |
|---|---|---|
| contextBlock.intent | 단일 요청 | 모델의 맥락체 갱신 블록이 작성/갱신 |
| contextBlock.progress | 단일 요청 | 계획 묶음 단위의 완료·미해결·남은 목표를 맥락체 갱신 블록이 작성/갱신 |
| contextBlock.focus | 개별 모델 호출 | **서버가 호출 직전에 구성하고 매 호출 교체**. 저장된 요청의 지속 필드처럼 다루지 않음 |
| contextData | 전체 방/세션 | overallFlow, currentTopic, details 등 세션 연속성 유지 |
| 원본 계획 | 개별 요청의 별도 기록/참조 | 맥락체 progress에 원문을 복제하지 않음 |
| 실제 실행 기록·산출물 | 개별 실행의 별도 기록/참조 | 모델이 말했다는 사실과 서버가 실제 실행·저장했다는 사실을 구별 |

- intent/progress는 **해당 조립 지침이 포함된 호출에서만 갱신**한다. 매 작업실 호출마다 자동 재생성하지 않는다.
- 맥락체 생성기는 focus의 존재를 알 필요가 없으며 intent/progress만 작성한다.
- contextData는 여러 요청에 의해 참조될 수 있으므로 저장/갱신 시 **세션 수준의 충돌 방지**가 필요하다.
- 정상 종결 시 Output은 실제 결과에 기초하여 최종 contextBlock과 contextData를 갱신한다. 최초 Corridor의 즉시 응답은 기존 1014 조립서대로 그 한 호출에서 languageBlock/contextBlock/contextData를 반환하며 동일 결과를 위한 불필요한 Output 호출을 반복하지 않는다.
- **[미확정]** 중단·실패 시 새 모델 호출로 맥락데이터를 갱신할지, 기존에 유효하게 갱신된 값과 확인된 사실만 보존할지의 세부 정책. 중단된 사실을 임의 성공으로 바꾸거나 갱신하지 않은 맥락체를 최신 생성값이라고 표현해서는 안 된다.

## 3. 전체 요청 처리 흐름

    요청 진입 (웹 채팅 또는 기타 근원지)
         |
         v
    roomId + requestId 확정, 요청별 실행 상태 생성
         |
         v
    서버의 계층 진행 제어
    Gate / Corridor / Workroom / Output
         |       ^
         |       | 필요시 복도회귀·재계획
         v       |
    지침 조립기 + 모델 호출기
         |
         v
    행동 검증 및 실제 실행, 결과 기록
         |
         +------> 실행 중 변화: SSE 이벤트 -> 프론트 임시 표시/캐시
         |
         v
    완료 / 중단 / 실패 -> 공통 최종화
         |
         +------> 영속 상태 확정 및 채팅·세션 데이터 반영
         |
         +------> 최종 스냅샷/버전 프론트 전송
         |
         v
    해당 요청의 활성 실행 수명 종료, 기록은 보존

- 위 그림은 **데이터와 제어 책임을 설명하는 도식**이다. 모든 계층이 반드시 각각 독립 LLM 호출이거나 모든 단계가 직렬로만 실행된다는 뜻이 아니다.
- 작업실이 하나의 모델 호출에서 여러 행동을 선택할 수 있고, 결과 의존성이 있으면 행동 단위로 호출을 분리할 수 있도록 경계를 유연하게 둔다.
- 모델 호출 방식(Function Calling/JSON), 지침 조립기, 작업실 내부 동작을 방/세션 저장 형식에 종속시키지 않는다.

## 4. 방 데이터: 소유권과 로컬 저장 구분

**핵심 원칙:** 미래 DB에 보관될 영속 데이터와 브라우저 로컬에서만 유효한 UI 상태를 **지금부터 명시적으로 분리**한다. 당장은 DB가 없으므로 영속 데이터도 로컬에 저장하지만, 그 사실이 '로컬 전용 데이터'라는 뜻은 아니다.

### 4.1 roomInfo

| 내용 | 목표 저장 위치 |
|---|---|
| 방 ID(roomId) | **DB 원본 + 로컬 임시 캐시** |
| 방 이름 | **DB 원본 + 로컬 임시 캐시** |
| 고정 여부 | **DB 원본 + 로컬 임시 캐시** |

### 4.2 roomChatInfo

**로컬 전용 UI 상태**
- 채팅 상단/하단의 스크롤 위치(스크롤 상태).

**DB 원본 + 로컬 임시 캐시**
- 입력기의 임시 입력(작성 중인 초안).
- 채팅 기록(사용자 메시지·생성된 응답 등).
- 각 채팅/요청의 **최종 맥락체**.
- 해당 방/세션 전체의 **맥락데이터**.
- 응답의 내용 및 진행 과정의 **순서와 내용**.
- 필요시 요청의 완료/중단/실패 사실 및 확정 실행 결과와의 참조. 정확한 개별 기록 형식은 별도 결정.

**SQL 조회 단위**
- SQL에서 채팅 내용을 방 전체 하나의 거대한 JSON으로 저장·조회하는 방식은 지향하지 않는다.
- 채팅을 **개별 기록 단위**로 나열하고, 각 항목은 소속 roomId를 가진다.
- 서버 API/RPC는 roomId를 조건으로 최근 또는 기준 위치 이전의 **n개 기록만** 페이지 단위 반환한다.
- 프론트는 먼저 받은 기록을 보여주고, 위쪽으로 올라갈 때 더 오래된 기록을 요청할 수 있다.
- **[미확정]** '채팅 한 건'을 사용자/AI 메시지 각 행으로 할지, 하나의 요청처리 묶음과 하위 메시지·진행 이벤트로 나눌지. 요청 ID와 메시지 ID가 다르다는 개념은 유지한다.
- **[미확정]** 정렬 기준, 커서, 검색/수정/삭제 및 초안 동기화 충돌 정책.

### 4.3 roomCanvasInfo

**로컬 전용 UI 상태**
- 인터랙티브 오블의 일시적인 동작·표시 상태.
- 캔버스 스크롤/뷰 위치(정확한 확대/축소·좌표 포함 범위는 후속 결정 가능).

**DB 원본 + 로컬 임시 캐시**
- 그 외 캔버스의 모든 지속 상태. 예: 스킬블록, 스킬블록 배치 좌표, 연결, 설정, 실제 적용된 변경 상태.
- 스킬과 스킬블록을 혼동하지 않는다. 재사용 가능한 스킬 **정의 자산**의 전역/워크스페이스 소유 범위는 캔버스에 배치된 **스킬블록 인스턴스**와 구별해 별도 설계한다.
- **[미확정]** 캔버스가 항상 방에 1:1로 소속되는지, 미래 여러 방에서 하나를 참조할 수 있는지. 이 노트에서는 사용자의 roomCanvasInfo 구분을 보존하며 소유권 확장은 임의 확정하지 않는다.

### 4.4 현재/미래 저장소 대비

| 분류 | DB 도입 전 | DB 도입 후 |
|---|---|---|
| 영속 방·채팅·캔버스 데이터 | 임시 로컬 구현으로 저장 | **서버/DB가 원본**, 로컬은 최근 API 결과의 캐시 |
| 로컬 전용 UI 상태 | 로컬 | 계속 로컬 |
| 실행 중 SSE 진행 상태 | 프론트 임시 실시간 표시 | 프론트 임시 실시간 표시 |
| 중요하고 확정된 실행 결과 | 현재 구현이 제공 가능한 로컬 저장·검증 경로 | 실행 단계에서 서버가 영속 기록 |
| 종료된 요청의 채팅/맥락 요약 | 현재 로컬 기록 | DB 기록 후 로컬 캐시 확정 |

**로컬 임시 캐싱의 의미**
- 사용자가 이전에 받은 서버 API 응답을 로컬에 임시 복제해서, 페이지 복귀·브라우저 재진입·오프라인 상태나 서버 조회 완료 전에도 기존 기록을 **우선 표시**할 수 있게 한다.
- 접속이 가능해 최신 API 결과가 도착하면 동일한 데이터 계약에 따라 캐시를 검증/갱신한다.
- DB 도입 전에도 화면 코드가 로컬 저장소를 영구 원본으로 가정하는 의존성을 만들지 않는다. 조회/갱신 인터페이스의 구현체만 임시 로컬로 둘 수 있다.
- 로컬에서 미동기화 변경을 허용한다면 그것은 단순 'API 응답 캐시'가 아니므로 별도 미동기화 상태·충돌 처리가 필요하다. **오프라인 편집 및 재동기화 정책은 아직 미확정**이다.
- 캐시가 보여 주는 내용이 현재 서버에서 최종 확정됐음을 보장하지 않을 때는 UI에서 '임시/오프라인' 상태와 구분할 수 있어야 한다.

## 5. 실시간 전달: 실행 중 SSE, 제어 명령 HTTP

### 5.1 방향

- **[현재 권장 방향] HTTP + SSE**: 프론트→서버는 일반 HTTP 요청(새 요청, 취소, 추가 입력 등), 서버→프론트는 요청별 진행/결과를 SSE로 전달.
- WebSocket이 필수라는 결론은 아니다. 향후 빈번한 양방향 실시간 협업이 필요해지면 다시 검토 가능.
- **[미확정]** SSE 연결을 방별로 둘지, 요청별로 둘지, 하나의 연결에서 여러 요청 이벤트를 다룰지의 최종 전송 구성.
- 모든 이벤트에는 **어느 roomId/requestId의 사실인지 식별할 방법**이 있어야 한다.
- SSE 연결 종료와 서버 요청 취소는 별개다. 일시적인 접속 종료만으로 요청을 자동 중단하지 않는다.

### 5.2 프론트의 실행 중 처리

1. 서버가 해당 요청을 수락하고 식별자를 제공한다.
2. 프론트는 해당 요청의 이벤트를 수신해 진행 상태·메시지 초안·실행 결과 등을 실시간 표시한다.
3. 이 표시에는 **아직 최종 확정되지 않은 정보**가 포함될 수 있으므로 임시 프론트 상태로 관리한다.
4. 서버가 영속 상태로 확정한 실제 스킬/스킬블록 변경은 해당 확정 사실과 버전에 따라 프론트 캐시에도 반영한다.
5. 최종화 시 서버의 최신 확정 스냅샷을 받아 캐시와 화면을 동기화한다.

모델이 '만들었다'고 말한 것과 실제 생성/저장이 완료된 것은 별개다. 영속 변경 이벤트는 검증·적용/저장 성공 이후 발생해야 한다.

### 5.3 동기화 버전

- **[권장 설계]** 서버가 요청 상태에 대한 단조 증가 revision 또는 동등한 이벤트 순서 식별자를 관리한다.
- 프론트는 HTTP 최종 스냅샷과 늦게 도착하는 SSE 이벤트의 순서를 비교하고, **낡은 이벤트로 최신 확정 상태를 덮어쓰지 않는다**.
- 프론트는 이벤트 누락 시 최신 상태를 다시 조회할 수 있어야 한다. SSE 이벤트 ID 및 재연결/재조회 정책은 후속 설계한다.
- 같은 방의 공용 자산(캔버스, contextData)에는 **요청별 revision과 별도로** 자산 자체의 버전/충돌 관리가 필요하다. 요청 ID가 분리됐다는 이유로 동시 수정 안전성이 확보되는 것은 아니다.

## 6. 중단 API와 요청 상태 수명

사용자 아이디어의 기본 형태:

    POST /api/stop             // URL은 임시 예시
    body: { targetRequest: requestId, roomId: roomId }

- 서버는 요청의 존재 여부와 호출 주체의 해당 요청 중단 권한을 검증한다.
- **접수된 중단 요청**과 **실제 중단 완료**를 구분한다.
- 진행 중이면 이후 계층 이동 및 신규 행동 실행을 차단하고, 해당 요청의 모델 호출/취소 가능한 실행에 취소 신호를 보낸다.
- 이미 저장·확정된 스킬, 스킬블록, 실행 산출물을 중단 버튼만으로 되돌리지는 않는다. **중단은 기본적으로 롤백이 아니다**.
- 중단 중이던 비취소 가능 행동은 실제 완료/실패 사실을 확인하고 마지막 확정 상태에 반영한다. 모델/외부 호출 취소가 항상 즉시 성공한다는 보장은 없다.
- 요청 A 중단은 별개 요청 B를 중단시키지 않아야 한다.
- **[권장 상태 구분]** running → stopping → stopped. 추가적으로 completed, failed 등은 사용하되 실제 상태 명칭과 전이표는 미확정.
- 이미 종결된 요청에 중단 API를 보냈을 때의 응답/중복 명령의 멱등 처리 규칙은 추후 결정한다.

### 6.1 중단 API 응답은 '상태만'이 아닌 최신 요청 스냅샷

**[합의된 방향]** 중단 응답에는 requestId만이 아니라, 프론트가 SSE 중간 상태와 대조해 최신 정보를 확인할 수 있는 **해당 요청의 현재 확정 상태 스냅샷**을 담는다.

최소한의 논의 대상 정보:
- 방/요청 식별자, 상태(running/stopping/stopped 등), 최신 버전
- 마지막으로 확정된 계층·계획 위치
- 마지막으로 **실제로 갱신된** contextBlock(intent, progress)
- 확인된 실행 결과·메시지·오류에 대한 유효한 정보 또는 참조

**서버 내부 requests 객체를 그대로 직렬화해 외부에 반환하지 않는다.** 내부 프롬프트·인증 정보·취소 제어기·민감한 참조가 존재할 수 있으므로 **프론트용 공개 상태 표현**으로 선별한다.

- HTTP 응답 시점에 실제 종료가 완료되지 않았다면 **stopping 상태의 최신 스냅샷**을 반환할 수 있다.
- 이후 실제 종료가 확정되면 **SSE 최종 이벤트 및/또는 상태 재조회**로 최종 스냅샷을 받을 수 있어야 한다.
- 중단 API의 접수 응답을 마치 모든 실행이 끝났다는 최종 확정으로 해석하면 안 된다.

## 7. 정상 완료·중단·실패의 공통 최종화

### 7.1 공통 절차 (사용자와 합의한 큰 흐름)

1. 해당 요청의 추가 실행을 막거나 종결 가능 상태에 진입한다.
2. 실제로 완료/실패/중단된 행동의 사실과 아직 남은 일을 정리한다.
3. 생성된 응답이 있다면 **그 응답과 진행 과정의 순서·내용**을 정리한다. 응답이 없으면 AI 답변을 임의 생성하지 않는다.
4. 마지막으로 유효한 **최종 맥락체**를 확정한다. 기존 갱신값을 보존하고 검증되지 않은 성공을 적지 않는다.
5. 적용 가능한 규칙에 따라 방의 **맥락데이터**를 갱신/확정한다(중단·실패의 정확한 갱신 계약은 미정).
6. 채팅 기록, 응답 내용, 요청 종결 사유/상태 및 필요 기록을 영속 저장한다. DB 도입 뒤에는 세션 맥락데이터와 채팅 기록의 일관성을 유지해야 한다.
7. 프론트에 **최종 확정 스냅샷 및 버전**을 전달하고 실시간 임시 표시를 이에 맞춰 확정/정리한다.
8. 요청의 활성 실행 수명을 종료하고 메모리상의 실행 제어 자원을 해제한다. **기록된 requestId·결과 자체는 삭제하지 않는다**.

**동일한 최종화 경로**를 정상 종결, 사용자 중단, 오류 종료에서 재사용하되, 각 사유의 결과/상태를 사실대로 남긴다.

### 7.2 DB 기록 시점은 '종결에 한 번만'으로 고정하지 않는다

최근 논의에서 최초 제안은 실행 중 SSE만 보내고 완료·중단 시 최종 기록을 DB에 저장하는 방식이었다. 검토 후 **중요한 확정 사실은 실행 도중에도 영속 기록하고, 마지막에 요청을 공통 최종화하는 방식**을 권장했다.

| 데이터 | 프론트 실시간 전송 | DB 도입 후 저장 시점(권장) |
|---|---|---|
| 현재 계층/작업 진행 표시 | SSE | 중요한 전환점은 기록 가능; 세부 빈도 미정 |
| 생성 중 언어 토큰·임시 문장 | SSE | 매 토큰 저장하지 않음, 확정된 결과만 |
| 실제 스킬·스킬블록/캔버스 변경 | 적용 확정 후 SSE | 변경 적용·확정 시 |
| 실제 실행 결과·산출물 | 확인 후 SSE | 결과 확정 시 |
| 맥락체 intent/progress | 필요한 시점에 상태 반영 가능 | 유효하게 갱신된 체크포인트 및 최종화 시 |
| 세션 맥락데이터 | 필요한 최종 갱신 안내 | 최종화 시 일관성 있게 저장 |
| 요청의 최종 응답·종결 사유·상태 | 최종 SSE/HTTP 응답 | 최종화 시 |

- 이유: 서버 재시작/크래시 전 실제 적용된 스킬블록이 있다면, 그 변경과 결과가 '기록에 존재하지 않는 일'이 되는 상황을 방지해야 한다.
- 최종화 DB 트랜잭션은 채팅 기록, 최종 맥락체, 맥락데이터 갱신 간 일관성을 지키는 방향으로 설계한다. **정확한 테이블/트랜잭션 묶음 및 장애 복구 로직은 추후 확정**한다.
- DB 저장이 실패했는데 성공이라고 안내하지 않는다. 재시도/복구/부분 성공 상태가 필요하며 상세 정책은 미정이다.
- 추가 실시간 메시지가 필요 없다면 모든 스트리밍 이벤트를 영속 로그로 남겨야 한다는 의미는 아니다.

### 7.3 최종 HTTP 응답과 SSE 이벤트의 역할

- 중단 요청의 HTTP 응답은 **현재 서버 상태를 확인/동기화**하는 역할이다. 중단이 완료될 때까지 기다리는지, 먼저 stopping을 반환하는지는 실행 상황과 별도 API 계약에 따른다.
- 정상 완료나 중단 완료의 최종 상태는 **SSE 최종 이벤트**로 전달할 수 있고, 재접속이나 이벤트 누락 시에는 상태 조회 API로 동일한 확정 데이터를 얻을 수 있도록 한다.
- 모든 경로에서 **서버가 확정한 상태가 우선**하며, 프론트는 받은 스냅샷을 버전 비교 후 반영한다.
- **[미확정]** 최종 객체를 이벤트에 전부 담을지, 참조/버전만 전달하고 API로 가져올지. 대용량 데이터·재연결 효율을 고려해 결정한다.
- requestId에 매달린 활성 SSE 처리가 끝나더라도 최종 기록 조회는 계속 가능해야 한다.

## 8. 동시 요청 및 충돌 처리

### 8.1 서로 다른 방·근원지

- requests[roomId][requestId]의 독립 실행 상태, 맥락체, 취소 신호, 결과 스트림을 섞지 않는다.
- 같은 서버가 여러 요청을 처리하되 요청별 상태 관리와 실행 예산을 분리한다.
- API 키가 여러 개라는 사실과 요청 격리는 별개다. 실제 Gemini 한도는 각 프로젝트 한도·429 상황을 기준으로 서버 차원에서 관리한다. 실측 사용량 증가·감소는 개발 완료 후 모니터링한다.

### 8.2 동일 방 안의 복수 요청

- 개별 요청 상태는 서로 독립적이지만, 같은 방의 **contextData** 및 같은 캔버스 자산을 변경하면 충돌 가능하다.
- **[권장]** 방/자산 버전 비교, 갱신 충돌 감지, 필요한 작업의 직렬화/재시도 등으로 무음 덮어쓰기를 금지한다.
- **[미확정]** 같은 방에서 요청의 시작·완료 순서가 다를 때 세션 맥락데이터를 어떤 순서로 병합할지, SQL 잠금 및 격리 수준, 구체적 충돌 복구 방법.

## 9. 사용자 경험 및 복구 시나리오

### 9.1 프론트 진입

- 캐시가 있다면 즉시 최근 기록을 보여준다(서버 확정의 최신성을 보장하지 않을 수 있음).
- 서버 API/RPC의 최신 기록 n개가 오면 비교·병합해 화면을 갱신한다.
- 로컬 전용 스크롤 위치·인터랙티브 오블 상태는 별도 보존한다.
- 오프라인에서는 마지막으로 받은 캐시를 볼 수 있도록 하되, 새로운 변경을 동기화하는 정책은 별도다.

### 9.2 실행 중 네트워크 끊김

- 연결이 끊겼다는 이유로 요청을 임의 취소하지 않는다.
- 재접속 후 요청 ID와 버전을 이용해 누락 이벤트를 복구하거나 최신 스냅샷을 조회한다.
- 서버가 이미 종결했다면 중복 실행 대신 최종 상태만 복원한다.

### 9.3 사용자가 중단

- 대상 방/요청 식별자와 권한 검증 -> stopping -> 실행 차단/취소 -> 실제 중단 확정 -> 공통 최종화.
- 중단 API 응답 스냅샷과 후속 SSE 이벤트가 순서가 뒤섞여 도착해도 버전을 비교하여 최신 결과를 유지한다.
- 이미 적용된 변경은 남고, 향후 되돌리기 기능은 별도 설계 대상이다.

### 9.4 서버 재시작·DB 기록 오류

- 진행 표시와 실제 실행 결과를 구분한다.
- 이미 확정된 영속 변경을 되살려 중복 실행하지 않도록 기록/멱등 처리가 필요하다.
- 최종 응답 기록과 세션 맥락데이터 갱신 중 하나만 성공하는 일을 방지하는 저장 일관성 규칙이 필요하다.
- **[미확정]** 무중단 재개를 어느 범위까지 지원할지, 활성 요청 상태의 DB 저장 주기 및 운영 장애 복구 정책.

## 10. 설계·개발 시의 구현 경계

1. **요청별 실행 상태 관리자**: 방/요청 ID, 현재 계층과 생명주기, 계획 참조, 중단, 최종화 판단을 담당. 워크룸 자체에 이러한 공통 책임을 흩뿌리지 않는다.
2. **맥락 관리**: 요청 범위 contextBlock과 세션 범위 contextData를 구분하고, 매 모델 호출 직전 focus를 만든다.
3. **지침 조립기**: 1014 계층 베이스 + 선택 공통 지침 + 서버 입력/출력 계약을 구성한다.
4. **모델 호출기**: 공급자 독립 인터페이스, JSON과 필요한 경우 Function Calling, 취소 및 제한 처리를 담당한다.
5. **실행·검증 영역**: 실제 스킬·스킬블록/IR 행동 결과를 기록하고 영속 변경 사실을 확정한다.
6. **데이터 접근 계층**: roomInfo/roomChatInfo/roomCanvasInfo의 'DB 원본 예정'과 '로컬 전용'을 개념적으로 분리한다. 지금은 임시 로컬 구현, 향후 서버 DB API+프론트 캐시로 대체한다.
7. **전송·프론트 동기화**: HTTP 요청 제어, SSE 진행 전달, 상태 조회/복구, 최신 스냅샷 및 revision 병합.

위 책임은 구현 경계 설명이며, 각 항목을 반드시 별도 디렉터리·클래스·새 변환 계층으로 만들어야 한다는 뜻은 아니다. 구체 파일명이나 TypeScript 도입을 전제하지 않는다. **기존 코드의 이름 및 구조를 억지로 보존하지 않는다.**

## 13. 10/16 추가 메모 — 요청처리객체 vs 호출처리객체

**이번에 잡은 핵심:** 요청 단위로 계속 살아 있는 데이터와, 모델을 한 번 호출할 때 잠깐 생기는 데이터를 무조건 한 객체에 섞지 말자.

### 요청처리객체 (요청 전체의 상태)
- 접근 표기는 `requests[roomId][requestId]`. 방 ID와 요청 UUID를 둘 다 쓴다.
- **처음 만들 때**: `roomId`, `requestId`, 요청 원문(`userRequest`), 전달받은 세션 `contextData`, 빈 `contextBlock`(`intent`/`progress`), `currentLayer`(시작은 Gate), `status`(시작은 running).
- `contextData`는 요청 시점의 세션 데이터로 전달받되, 실제 세션 원본과 혼동하거나 종료할 때 무조건 덮어쓰지 않는다.
- **필요해질 때 추가**: `plan`, `planIndex`(혹은 이에 해당하는 계획 위치), 확정된 실행 결과·진행 기록 등. 시작부터 불필요한 빈 필드로 가득 채울 필요 없음.
- `focus`는 여기서 오래 보유/계속 덧수정하는 값이 아니라 **모델 호출마다 서버가 구성하는 값**.
- 실행 중인 요청의 중심 상태이며, 완료·중단·실패 시 공통 최종화를 거쳐 기록으로 남긴다.

### 호출처리객체 (이번 호출 자체의 작업 공간)
- **같은 색인 방식**: 예시 `calls[roomId][requestId]`. 이 표기는 해당 요청의 **현재 호출**을 가리킨다고 이해하면 편함.
- 한 요청에 모델 호출은 여러 번 있을 수 있다. 병렬·지연 응답이 생기면 호출 순번/ID를 추가로 고려해야 함.
- 이번에 조립한 모델 입력/지침, 응답 원문, 검증·해석 결과, `need`, 오류 등 **호출 한 번의 입출력**을 관리.
- 호출 결과 중 다음에 필요하거나 사용자에게 보여줘야 하는 것만 요청 상태·실행 기록·프론트에 반영하고, 불필요한 중간 입력/응답은 정리한다.
- 서버 내부 호출 객체 자체를 프론트에 그대로 반환하지 않는다.

### 동작 흐름 (개념)
```text
요청처리객체(요청 전체 상태)
  ↓
호출생성기: currentLayer / planIndex / 맥락체 / contextData / 이전 결과·need 조회자료 참고
  → 필요한 지침 조립 + 데이터 채움 + 현재 호출용 focus 구성
  ↓
호출처리객체: 이번 호출 입력·응답 관리
  ↓
호출처리기: 응답 검증·해석, need / plan / languageBlock / contextBlock / contextData / 행동 등 구분
  ├─ languageBlock → 프론트 표시 + 채팅/진행 기록
  ├─ contextBlock → 허용된 필드만 요청처리객체에 갱신
  ├─ plan → 요청의 계획 상태로 반영
  ├─ need → 데이터 조회 → 다음 호출의 입력 자료로 연결
  ├─ contextData → 세션 갱신 절차로 연결(원본 충돌 확인)
  └─ 실제 행동 → 요청사항 실행기
                      ↓
                 실행 결과 확인·확정·기록
                      ↓
                 요청 진행 상태/현재 계층/계획 위치 갱신
                      ↓
            다음 호출생성기로 순환 / 공통 최종화
```

**중요한 구분**
- 호출처리기가 행동을 **해석**하는 것과 실제 실행이 **성공**한 것은 별개. 성공 표시·캔버스 변경 알림은 실행기가 확인한 뒤.
- 모든 모델 반환값을 요청사항 실행기로 보내는 건 아님. 언어·맥락·계획처럼 검증 후 상태에 반영하는 것과 실제 실행 행동은 갈라진다.
- 실행기는 검증된 결과를 기록한다. **다음 호출의 `focus`는 호출생성기가 그 결과와 위치를 보고 새로 만든다.** 실행기가 맥락체의 focus 문자열을 직접 누적 편집하지 않음.
- `need` 자체와 조회 결과는 다름. 필요한 결과는 다음 호출에 넘기되 맥락체에 원문/로그를 복제하지 않음.
- 데이터는 **요청 전체에 유지 / 이번 호출만 사용 / 최종 기록 필요**라는 수명 기준으로 나누는 게 우선. 이것 때문에 별도의 변환 계층이나 새로운 클래스를 억지로 만들 필요 없음.
- `calls[roomId][requestId]`, `planIndex` 같은 구체 이름·정확한 하위 구조·호출 병렬성은 아직 완전 확정이 아님. 역할과 데이터 흐름만 우선 정리한 것.

## 추가 미확정 계약 — 작업실/계층
