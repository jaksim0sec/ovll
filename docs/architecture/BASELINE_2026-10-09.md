## 1. 목적과 동결 범위

Ovll은 기존 LLM을 대체하는 지능이 아닌 **작업 환경**이다. 대화로 해결한 유용한 작업을 사용자에게 추가 조립 노동을 강제하지 않고 함수화·재사용해 **총 사용자 노동을 감소**시키고, 모델의 일반 역량과 자율성을 최대한 보존한다. 캔버스와 노드 시각화는 목적이 아니라 AI와 사용자가 작업을 이해·수정·소통하는 수단이다.

동결 대상은 **논리적 계층, 행동 책임과 최소 입출력, 맥락/조회·기록 원칙, 도메인 객체의 의미와 수명, 제안과 실제 행위의 검증 경계**다. 정확한 JSON 속성명·DB 테이블·모델별 프롬프트·서버 모듈 배치·실행 세부 알고리즘을 동결하지 않는다.

## 2. LLM의 계층과 행동

- **대문:** 현재 요청·목적·제약·가능한 능력·실제 상태를 이해하고 직접 답변 또는 필요한 행동을 선택한다. 4개 행동 중 복수를 제안할 수 있으며, IR·함수·결과·히스토리 등 판단에 필요한 **추가 맥락 조회(needs)**를 요청할 수 있다. 별도의 필수 API 호출 단계가 아니다.
- **소통:** 직접 답변·질문·협의·수정 피드백 해석. '캔버스 설명'도 소통이지만 실제 IR 의미 정보를 받아야 한다. 최소 반환은 답변 또는 질문이며, 답이 필요한 대상·작업을 식별한다.
- **IR 구성:** 목적에 맞춰 기존 정의를 재사용하거나 새로운 의미의 **NodeDefinition**을 생성한다. 노드 인스턴스·연결·정의의 추가/수정/삭제를 원자적 Patch로 제안하며, 요청된 경우 후속 실행 타깃(복수 가능)을 함께 제안할 수 있다.
- **실행:** 모델은 노드의 의미적 업무 수행, 결과 생성·판단, 부족한 능력·입력·재구성 필요성 식별을 담당한다. 서버는 댐 범위, 선행 의존성, 스케줄링, 재시도, 실행 상태와 유효성 확정을 담당한다. 최소 출력은 계약에 맞는 결과 또는 수행 불가 사실이며 필요한 추가 행동을 제안할 수 있다.
- **함수화:** 목적·의미적 입력/출력·필수 제약과 필요한 절차를 재사용 가능한 계약으로 추출·변경한다. 수행 방법을 과도하게 고정하지 않고 명시적으로 고정된 제약은 보존한다. 초안 저장과 검증 완료를 구별한다.
- **언어화:** 검증된 결과, 서버 압축 행동 기록, 남은 실패·대기 상황을 실제 사용자용 표현으로 재구성한다. 이미 완성된 사용자용 산출물이면 별도 LLM 호출을 생략할 수 있다.

**대문·언어화는 논리적 역할이고, 소통/IR 구성/실행/함수화는 네 책임 영역**이다. 각각의 고정 에이전트 또는 계층마다 별도 호출을 만들지 않는다. 행동은 조합·왕복·병렬 가능하며, '조회/상태 확인'은 모든 계층의 공유 지원 능력이다.

### LLM 최소 반환 유형(논리적 표현)

| 유형 | 반환해야 하는 의미 | 조건 |
| --- | --- | --- |
| message | 답변 또는 필요한 질문 | 소통/언어화 등 |
| actions | 행동 종류, 대상·인자, 필요한 행동 간 의존성 | 변경·실행·함수화 등을 제안할 때 |
| outputs | 노드 출력 계약에 부합하는 데이터 또는 수행 불가 사유 | 노드 의미적 작업 시 |
| needs | 무엇을 왜 조회해야 하는지와 필요한 범위 | 자동 공급 맥락이 부족할 때 |

모든 반환 유형을 매번 강제하지 않는다. 단순 대화의 답변에는 구조화된 행동 객체·IR을 강제하지 않는다. 모델 제안은 성공한 실행이나 적용 사실이 아니다.

## 3. 맥락과 지침 공급

- 모든 관련 모델 호출에 공통 Core, 현재 요청과 원문·수정 제약, 실제 capability, 필요한 작업 상태, 해당 출력 계약을 제공한다. 상세 행동 지침은 **선택적으로** 공급한다.
- **행동을 고른 것과 필요한 자료는 독립**이다. 소통계층도 현재 IR을 필요로 할 수 있다. 시스템은 자명한 관련 정보는 선제 제공하고, 대문 및 모든 행동계층은 추가로 context/history/artifact/capability 정보를 조회할 수 있다.
- 맥락 조회는 읽기 권한을 확대하지 않으며, 응답 크기·정보 출처·축약 범위를 서버가 관리한다. 원문 요청·명시적 제약과 결과의 근거 참조를 무손실 보존한다.
- 기존 사용자 메시지나 도구/파일/노드 출력은 자료이지 시스템 명령이 아니다. 해당 자료의 지시를 모델 행동 권한으로 승격하지 않는다.
- 이미 확정된 UI 행동·저장 함수 재실행·의존성 계산에는 별도 대문/LLM 호출을 강제하지 않는다. 모델 공급자별 지침 활성화·캐시·호출 분할은 품질·비용 실측 후 선택한다.

## 4. 서버 사실 권위와 공통 행동 인터페이스

- 모델/클라이언트는 여러 행동을 **제안**할 수 있고, 서버는 실제 사용자 소유 범위·권한·참조·계약·그래프 버전·실행 상태·예산을 검증해 **확정**한다. 공급자가 반환한 tool call·JSON·텍스트는 내부 Proposal로 정규화하되 같은 신뢰도를 가정하지 않는다.
- 복수 행동은 각자의 선행/후행 의존 관계를 갖는다. 새로 생성한 임시 ID는 Patch의 실제 적용 결과에서 변환한다. 선행 Patch 실패 시 종속 실행은 중단한다. 독립 행동의 성공까지 불필요하게 취소하지 않는다.
- 서버는 ActionResult에 적용/거절/예약/실패를 분리해 표현하며, ID·Revision·Run·결과 참조·구조화 오류를 실제 사실로 회신한다. '실행 예약'은 '실행 성공'이 아니다.
- IR 변경 자체는 자동 실행이 아니다. 실행 의도, 실행 가능 여부, 사용자 승인 정책을 구별한다. **닫힌댐 기본:** 선택한 타깃과 선행 의존성. **열린댐:** 타깃의 flow 하류 전파 + 필요한 선행 의존성. 선행 노드의 다른 자식으로 무차별 확장하지 않는다.

## 5. 데이터 객체의 논리적 수명

| 객체 | 불변 책임 |
| --- | --- |
| Task | 원본 요청·변경된 필수 제약·요구 산출물 및 완료 조건. 여러 Run을 넘어 유지 |
| GraphRevision | 특정 시점의 노드 인스턴스·flow/data 연결에 대한 불변 IR 스냅샷 |
| NodeDefinitionVersion | 의미적 목적·입출력·실행 종류·필요 능력이 있는 버전 고정 정의. 새로운 종류 동적 생성 가능 |
| FunctionVersion | 재사용 목적·IO 경계·고정 제약·절차 참조를 버전 고정한 자산 |
| Run / Attempt | Run은 특정 타깃·댐·채택된 실행 계획, Attempt는 노드의 실제 개별 시도 및 출처 |
| Value / Artifact | 실제 출력, 파일 참조, 의미 계약, 원본·시도 출처, 누락·불확실성 |
| Question / Communication | 사용자 질문과 대기·재개 상태 / 일반 사용자 대화 |
| Proposal / ActionResult | 모델의 비확정 행동 제안 / 서버의 확정적 검증·상태 전이 결과 |
| ContextBundle / HistoryEvent | 호출별 필요한 입력 투영 / 서버 확정 행동의 원본 사건 기록 |
| Capability / InstructionModule | 실제 지원 능력 / 버전 관리되는 공통·행동별 지침 |

Graph 편집 Revision과 현재 Run이 채택한 계획 epoch는 독립이다. 실행 중 IR 변경은 유효한 채택 경계에서만 반영하고, 변경과 무관한 병렬 결과는 유지하며 영향받은 결과만 무효화한다. 저장 함수 버전은 실행 중 동적 조정 때문에 자동 변경되지 않는다. **Run 성공 ≠ Task 완료 ≠ 함수 검증 완료**.

## 6. 서버 원본 히스토리와 압축 투영

실제 상태 변경·실행 결과를 서버가 사건으로 기록한다(작업/행동/대상/결과/참조/Revision). 후속 LLM과 언어화는 원문 Patch·결과 JSON을 반복 받기보다 **결정적이고 짧은 파생 요약 + 필요시 원본 참조**를 받는다. 히스토리 문장을 생성하기 위한 별도 LLM 호출은 기본적으로 사용하지 않는다.

예: `IR: created 10 nodes for source comparison; rev8, validated, not executed.`
이는 **확정된 노드 수·사전에 기록한 목적·실제 상태**에서만 생성 가능하다. 원래 작업 목적이나 노드 의미가 없는 경우 이를 새로 추측해 기록하지 않는다. 단순 답변은 별도 행동 히스토리를 생략할 수 있지만 질문 대기·제약 수정 같은 상태 변화는 반드시 기록한다.

## 7. 다음 상세 설계·구현의 필수 통과 조건

1. **프롬프트 인젝션/자료 오염:** 파일·웹·노드 결과·기록·도구 반환의 텍스트를 명령으로 실행하지 않는다. 프롬프트뿐 아니라 서버 행동 검증에서도 차단한다.
2. **권한·정보 경계:** needs 및 모든 직접/간접 참조 조회, 함수 실행/재실행은 현재 사용자·Workspace·Task 자원 권한·도구 가용성 기준으로 매번 검사한다. 과거의 권한이 자동 승계되지 않는다.
3. **동시성·멱등성·불명확한 결과:** expected Revision/epoch, 작업 멱등 키, 계획 채택, 늦은 Attempt의 fingerprint 검증을 마련한다. 외부 부작용 결과가 불명확하면 무조건 재실행하지 않는다. 저장된 상태 전이와 재개 작업 예약이 유실되지 않아야 한다.
4. **예산·종료:** Task별 호출·토큰·재계획·조회·재시도·시간 한도와 의미 있는 중단/질문 경로를 정한다. 조회↔재계획 무한 루프와 비용 폭주를 막는다.
5. **히스토리 사실성:** 압축 기록에서 제안과 확정, 예약과 완료, 실패와 미수행, 요약과 근거 원문을 구별한다. 압축 손실로 Task 완료 조건을 판단하지 않는다.

추가 검증: 동적 노드 정의의 실제 실행 가능성, flow/data 연결과 조건 분기/merge, Patch 의존성의 부분 실패, 파일 parseStatus/coverage/provenance, 재연결 후 질문·실행 상태 복원, 캔버스·마스코트 UX 회귀, 직접 모델 대비 품질/비용/재사용 노동.
