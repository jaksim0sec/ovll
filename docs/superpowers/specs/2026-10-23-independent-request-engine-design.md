# Ovll — Independent Request Engine Design

상태: Superpowers 설계 검토용. 구현 완료나 기존 런타임 계약의 선언이 아니다.
대상: beta. main 변경·병합·배포 금지.

## 목표와 비목표

하나의 가상 요청을 등록소/대기열에 넣고, 외부 서버·DB·프론트 연결 없이 엔진을 실행한다. 독립 AI 호출기와 자료 공급자를 주입하여 **Gate → Hallway Initial → 직접 응답·확정**을 실제 Gemini로 실행할 수 있게 한다. 모의 모델을 이용한 결정적 회귀검증도 제공한다.

엔진은 데이터의 물리적 저장 위치, Gemini SDK/API, HTTP/SSE, 프론트 DOM, 파일 저장소를 알지 않는다. 초기에는 요청 하나만으로 시연하지만 복수 요청의 격리와 공통 처리기 재사용을 검증한다. Workshop 실행, IR·Saved Function, Canvas 원격 수정, 인증·네트워크 API·SSE, 서버 DB·실파일 전송·재시작 후 복구는 본 단계 범위 밖이다. 미구현 실행을 성공으로 가장하지 않는다.

## 결정된 용어

대문 **Gate**, 복도 **Hallway**(Hallway Initial, Hallway Return), 작업실 **Workshop**, 종결 **Output**. 기존 Corridor/Workroom은 신규 코드·현행 docs·prompts에서 사용하지 않는다. 프롬프트 베이스 및 manifest 계층 식별자는 hallwayInitial/hallwayReturn로 정리한다. 기존 docs/developing/workrooms.md는 workshops.md로 변경하고 전 참조를 수정한다. 사료·과거의 명칭을 별도의 런타임 호환 계층으로 유지하지 않는다. 변경 전 docs/·prompts/ 모든 파일을 순회하여 문자열, 설명, 파일명, 상대경로 및 JSON 키를 검사한다. 기존 메시지의 의미와 Gate·Hallway·Workshop·Output 역할을 변경하지 않는다.

## 시스템 경계

1. **등록소(Request Registry)**: roomId와 requestId로 개별 요청·상태·중간/최종 검증 결과를 관리한다. 모델 호출 순간의 임시 객체와 분리한다. 최초 개발용 저장은 프로세스 메모리이며 영속 저장을 가장하지 않는다.
2. **대기열/관제(Scheduler)**: 접수된 요청의 실행 순서를 결정하고 공통 엔진을 호출한다. 최소 구현의 동시 실행 한도는 1이다. 요청이 대기열에서 빠져도 등록소에서는 조회 가능하다. 향후 한도를 변경해도 엔진의 요청 입력 구조를 변경하지 않는다.
3. **독립 엔진(Engine)**: 확정된 레이어 입출력에 따라 프롬프트를 조립하고 AI 호출기 응답을 구조·의미 검증하며 각 요청의 단계 전이를 결정한다. 범용 엔진은 Gemini 이름, SDK, 인증, 모델 선택 로직을 import하지 않는다.
4. **AI 호출 포트**: 엔진의 모델 중립적 호출 명세를 공급자용 요청으로 변환하고, 공급자 응답을 모델 중립적 결과로 정규화한다. 처음에는 모든 레이어에서 Gemini 단일 모델을 사용하며, 실제 모델 ID와 비밀키는 호출기 설정으로 전달한다. 엔진이 공급자 변경으로 수정되는 것을 금지한다. 모의 호출기는 동일 포트를 구현한다.
5. **자료 공급 포트**: Gate가 요청한 need를 해결한다. 최초 구현은 메모리/시험 자료를 제공한다. 이후 프론트·DB 조회는 이 포트의 구현을 바꾸는 것으로 확장한다.
6. **결과 확정**: 구조 검증과 단계 판정은 엔진 책임이다. 검증된 직접 답변만 completed로 표시한다. plan이 나오면 미구현 Workshop은 실행하지 않고 **unsupported_workshop**으로 기록한다.

등록소·큐·엔진·호출 포트는 책임 경계이며 각각 거대 프레임워크나 클래스를 만들어야 한다는 뜻이 아니다. 단일 공통 엔진 구현을 여러 요청이 사용하되, 요청별 맥락체·호출 결과는 서로 섞지 않는다.

## 요청 시작 데이터

입력은 구조화된 사용자 초안(parts 배열의 text/skill/block 구별)과 요청 시점의 초기 자료 묶음이다. 텍스트 안에 태그 문법을 합성하지 않는다. 명시적으로 첨부된 Skill은 해당 Skill에 대한 사용 가능한 정의, Skill Block은 **그 블록 인스턴스 전체 + 참조하는 Skill의 사용 가능한 정의**를 요청 접수 시점에 공급한다. 연결된 다른 블록이나 전체 그래프는 자동 주입하지 않는다.

초기 프로토타입에서 자료 해석·전달 책임은 프론트 측이다. 현재 beta의 front/js/skill/catalog.js 및 readSkillCatalog()는 **표시용 Skill 메타데이터**만 제공하며 실제 실행 Skill 정의/지침이 아니다. 이 둘을 구분하는 출처·완전성 메타데이터를 유지하고, 없는 실행 정의를 만들어내지 않는다. 초기 참조 ID를 못 찾은 경우에는 누락을 명시하며 다른 임의 대상의 정보로 대체하지 않는다. Blob·파일 본문은 현재 exportCanvasJSON()에 포함되지 않으며 실행 IR과 동일시하지 않는다.

자료를 이미 받아도 Gate 자체를 생략하지 않는다. **InformationRequestBlock**은 제공된 자료로 충분한지 판정하고 추가 need만 작성한다. Gate 모델 입력에는 최초에 제공된 자료의 범위·완전성·누락 여부를 함께 제시한다. need 문법은 기존의 [[datasetName,...parameters],...] 유지(originalReq, chatContext, skillDef, canvasSkill, skillList 등); 이미 확보한 완전 동일 대상의 자료는 다시 외부에 요청하지 않고 재사용한다. 표시용 메타데이터만 있는 경우 완전한 실행 정의를 확보했다고 간주하지 않는다. 해당 자료를 실제로 제공할 수 없다면 응답을 '자료 없음/미지원'으로 전달하며 성공한 조회라고 표현하지 않는다.

이 최초 자료 입력과 need 결과의 공통 규격은 '자료의 식별자/종류, 값, 출처, 완전성 또는 부재 여부'를 표현할 수 있어야 한다. 이를 별도의 네트워크 프로토콜이나 DB 스키마로 고정하지 않는다. 공급자의 응답은 엔진이 소비하는 정규화 형식으로 검증한 다음 다음 AI 호출에 전달한다. 필요 자료가 없으면 근거 없는 추론으로 메우지 않고 실패 또는 범위 제한을 기록한다.

## 레이어 계약과 분기

프롬프트는 prompts/manifest.json에 지정된 순서(common concepts → base → common JSON 규칙 → 활성 블록)로 조립하며, 공급자의 모델 입력 형식은 AI 호출기 측에서 변환한다. 활성화되지 않은 JSON 필드는 요구하거나 적용하지 않는다.

- Gate 입력: 사용자 원요청, 기존 contextData, 초기 주입 자료·완전성. 출력: {need:[...]}. Gate는 계획·실행·contextBlock 생성 금지.
- Gate 이후: need를 자료 공급 포트로 해석하고, 초기 자료와 중복되는 유효 데이터는 재사용한다.
- Hallway Initial 입력: 사용자 원요청, contextData, Gate 자료. **직접 응답 분기**의 반환은 {languageBlock,contextBlock:{intent,progress},contextData:{overallFlow,currentTopic,details}}. 이 분기는 추가 Output 호출 없이 확정한다.
- **계획 분기**의 반환은 {plan,contextBlock:{intent,progress}}뿐이다. 최초 구현은 plan을 검증·기록하지만 Workshop 동작을 실행하지 않는다. 미구현을 완료/종결로 표현하지 않는다.
- Hallway Return, Workshop, Output의 의미/프롬프트는 유지하고 이름만 통일한다. 최초 프로토타입은 이 레이어들을 가짜로 호출하거나 실행 완료 처리하지 않는다. Output 처리 구현이 늘어나는 요청마다 복제될 필요는 없다.
- 서버가 결정한 현재 계층/검증 사실과 모델이 출력한 주장은 구분한다. focus는 호출 때 생성하는 서버 전용 정보이며 요청 영속 상태에 누적하지 않는다. contextData는 세션 원본과 구분한 초기 스냅샷을 사용하고, 다중 요청의 무음 덮어쓰기를 허용하지 않는다.

## 최소 수명과 실패

메모리 등록소의 요청 상태는 queued → running → completed | unsupported_workshop | failed 로 제한한다. 실패 원인은 검증 오류, 모델/자료 공급 오류, 지원되지 않는 추가 자료 등을 구별 가능한 정보로 남기되 비밀키·원문 프롬프트를 사용자 공개 결과에 섞지 않는다. 이 구현에서 중단·재시작 복구·영속 Revision은 미지원이라고 명시한다. 전송 연결 끊김과 요청 취소를 동일시하지 않으며, 추후 외부 통신 계층은 엔진을 호출하는 출발점으로만 연결한다.

AI 호출 포트는 입력의 프롬프트·데이터·JSON 요구·선택적 취소 신호를 받아 정규화된 결과 또는 명시적 오류를 돌려준다. 공급자별 토큰 제한·429·인증·응답 포맷은 포트 구현이 처리한다. 최종 반환의 JSON 구조·분기별 필드 및 의미 검증은 엔진이 담당한다.

## 구현/검증 순서

1. docs/와 prompts/ 전체 순회 및 Gate/Hallway/Workshop 용어·manifest·경로 일괄 통일; 참조 무결성 검사.
2. 메모리 등록소와 요청 큐/관제: 테스트 요청 1개 접수·조회·상태 기록; 2개 테스트 요청으로 상태 격리 확인.
3. 프롬프트 조립, 모델 중립 호출 포트, 모의 Gemini 대체 호출기와 실제 Gemini 호출기(키는 소스에 포함하지 않음).
4. 구조화 초안의 직접 참조 초기 데이터 공급, 중복·누락 처리 및 need 공급 계약.
5. Gate → Hallway Initial의 실제 검증·직접 응답 확정, 계획 분기 unsupported 처리; 정상/오류/누락/중복/복수 요청 테스트.
6. 유효한 공급자 자격증명이 있을 때 실제 Gemini 단일 요청을 종단 검증; 키가 없으면 이를 미검증이라고 표시한다. 모의 응답을 실제 Gemini 성공으로 가장하지 않는다.

최초 프로토타입은 의도적으로 서버 HTTP API와 프론트 실제 전송 코드를 연결하지 않는다. 추후 프론트 요청 진입점, 영속 DB, HTTP/SSE, 파일 전송, 복수 모델은 이 계약의 바깥 어댑터/공급자를 통해 추가한다. 기존 main 코드나 실행 GraphPatch/ModelTurn을 신규 계약으로 강제하지 않는다.

## 완료 기준

- 실제 요청 단위의 등록·큐잉·실행·조회가 존재하고 정상/실패/미지원 상태가 구별된다.
- 엔진이 공급자 SDK와 독립이며 Gemini/모의 호출기를 동일한 인터페이스로 교체할 수 있다.
- Gate가 이미 초기 전달된 참조 데이터를 재요청하지 않도록 정보 전달·중복 해소가 확인된다.
- Hallway 직접 응답만 완료 처리하고, 계획 분기는 조용히 성공 처리하지 않는다.
- 문서·프롬프트·manifest와 해당 소비자의 용어/경로/키가 일치한다.
- 모든 성공 주장은 실제 실행된 검사 결과에 한정한다.
